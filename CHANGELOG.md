# Changelog

All notable changes to DAORework are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/). Task IDs refer to [docs/ROADMAP.md](docs/ROADMAP.md).

## [Unreleased]

### Changed
- The Mods tab is in sections (P2.5-17): *Library*, *Installed by hand* (with how many mods it found), *Load order*, *Changes* and *Folders*, one at a time instead of one long page. Each plan shows in the section you asked for it, and the *Adopt* next step opens *Installed by hand*.
- Plans in the window are easier to read (P2.5-18): each opens with one sentence saying what it does (*Copies 1 file and deletes 1. Writes 3 B.*), its warnings follow in full, and the file-by-file detail is behind *Show details*. Mods are named by their names instead of ids like `eyes-bd85c991`. The command line's plans are unchanged.
- Each backup says what its change did (P2.5-19): the Mods tab's *Changes* and the Fixes tab name each backup by its change (*Activated Eyes and Nails*, *Adopted 4 mods: …*, *Changed the load order*, *Applied 4 GB patch*), and asking to roll one back names it too. Mods are named by their Library names there, and fixes by theirs (*4 GB patch*, *DXVK*), instead of their ids.

### Added
- *Installed by hand* fills in by itself (P2.5-16): the Mods tab lists the mods you installed by hand as soon as a profile is chosen, and again after every change, without pressing a button. It only reads. *Look again* reads it once more after you add files by hand.
- Adopt several mods at once (P2.5-13): each mod in *Installed by hand* on the Mods tab has a tick box, with *Select all* and *Clear*. *Adopt selected* shows one plan for every ticked mod, applied with one backup and undone by one rollback, as `mods adopt <id>...` does on the command line.
- Activate or deactivate several Library mods at once (P2.5-14): each mod in the Library has a tick box, with *Select all* and *Clear*. *Activate selected* plans every ticked mod that is not active, and *Deactivate selected* every ticked mod that is, each as one change with one backup, as `mods activate <id>...` does on the command line.
- Import several downloads at once (P2.5-15): *Import a mod* on the Mods tab lets you pick several files in one go, as dropping several already did. Each is scanned and checked as before, and one message lists what was imported.

## [0.3.1] - 2026-10-31

The same program as 0.3.0, now code-signed, and the first release published to Nexus by the release workflow.

### Changed
- `DAORework.exe` and `dao.exe` are code-signed ([ADR-0018](docs/adr/0018-mod-safety.md) §4): Windows names the publisher, which you can check under Properties > Digital Signatures. A new publisher still builds up reputation with Windows SmartScreen, so it may warn on the first releases. Each release keeps its `.sha256` and its build attestation.
- Releases can go to Nexus Mods by themselves ([ADR-0024](docs/adr/0024-publishing-releases-to-nexus.md)): once the owner adds the Nexus API key and file id to the release environment, each tag uploads the same zip as the GitHub release to the [Nexus page](https://www.nexusmods.com/dragonage/mods/7083) as a new version of the main file. The app itself still never goes online.

## [0.3.0] - 2026-10-31

Phase 2.5 (launch-ready mod manager), the first public release. Everything the command line does with mods, fixes and saves is now in the window, and a player who already mods by hand can hand that setup over to DAORework without reinstalling anything. Every mod is checked before it enters the library: programs are named and never installed, your own antivirus scans it, and a download that differs from the official one is pointed out. As before, nothing is written to your folders without a plan you confirm and a backup you can roll back to. GOG and EA App installs are detected but have not yet been run on a real machine ([#5](https://github.com/arastella625/DAORework/issues/5)).

### Added
- Custom looks (P2.5-11, [ADR-0017](docs/adr/0017-custom-looks.md)): under the theme picker on the Settings page, *Your looks* makes a look from the theme on screen, with a name, the theme it starts from and an accent of your own. The app keeps your accent's hue and adjusts its lightness until text on it passes AA, and refuses reds, which are kept for danger (`DAO_LOOK_ACCENT_RESERVED`). A look can have a picture of your own behind the pages (PNG, JPEG or WebP, up to 50 MB; DAORework keeps a copy no larger than 3840 px and never changes your file), tinted toward the theme's colors and veiled with its background. Sliders set the tint, the veil and the blur, and whether the picture fills the window or fits inside it. The veil never goes below the floor DAORework works out from the picture's brightest part, so text over it stays readable, and the Settings page says what that floor is. Picking a look previews it at once; *Use everywhere* makes it the app-wide look, and *Delete* takes a second click. On the Profile page each launch profile can have its own look (a custom look or a built-in theme) that shows while it is selected, or use the app-wide one. Looks live in `looks\<id>\` in the app-data folder and the choices in `preferences.json`. A look or picture that is gone or damaged falls back to the app-wide look, or to the look without its picture, with a warning in the log.
- Every mod is scanned by your own antivirus before it enters the library ([ADR-0018](docs/adr/0018-mod-safety.md), P2.5-12): `mods import` and adopting pass each file through the Windows antimalware scan (AMSI), which hands it to Microsoft Defender or whatever antivirus is installed. If it reports a file, or your administrator's policy blocks it, the mod is refused and nothing of it is kept (`DAO_MOD_SAFETY_THREAT_FOUND`); there is no override in DAORework. Programs are scanned in full and data files up to 256 MB each. When no antivirus answers (or not on Windows), the mod is imported and shown as *not scanned*, with the reason. DAORework itself sends nothing anywhere, and never calls a mod safe: a clean scan reads "No threats found by the Windows antimalware scan (AMSI)".
- Known downloads are recognized ([ADR-0018](docs/adr/0018-mod-safety.md), P2.5-12): the catalog records the SHA-256 of official downloads (Qwinn's Fixpack 3.5 and Extra Dog Slot 1.41 so far), and `mods import` says when a download is one of them. A download of a mod the catalog knows that matches none of them gets a warning with the mod's page (`DAO_MOD_SAFETY_DOWNLOAD_DIFFERS`); it is still imported, because authors update their files.
- `mods import` reads `.7z` and `.rar` downloads (P2.5-04), through SharpCompress (MIT). They go through the same checks as a `.zip`: a path that would leave the mod's folder refuses the whole archive, and an archive that cannot be read (damaged, truncated, password-protected or one part of a split archive) is refused with nothing added to the library (`DAO_MOD_IMPORT_INVALID`) and a hint to download it again. A `.7z` holding a `.dazip` is unwrapped like a Nexus `.zip`.
- The window's Mods tab has a *Library* (P3-04): every mod in DAORework's library with its files, size and source, what your antivirus said, the program files it holds, and whether its download is a known one, a download that differs from the known ones shown as a warning. *Import a mod* and *Import a folder* add to it, and so does dropping `.dazip`, `.zip`, `.7z` or `.rar` files on it. Importing installs nothing.
- Mods are activated and deactivated from the window's *Library* (P3-04), as `mods activate` and `mods deactivate` do: *Activate* or *Deactivate* on a mod shows the plan for the profile's documents folder first, and nothing changes until *Apply*; a blocked plan cannot be applied, and *Cancel* changes nothing. The change is backed up and journaled like any other, and each mod shows whether it is active.
- The window's Mods tab has a *Changes* panel (P3-04), as `mods status`, `mods rollback` and `mods recover`: what is active in the profile's documents folder, the backups most recent first with what was active before each, *Roll back to before this* asked once more before anything is put back, and, when a change did not finish, *Finish it* or *Roll it back*.
- Mods installed by hand are adopted from the window (P2.5-03, P3-04), as `mods adopt` does: *Adopt* on a candidate in *Installed by hand* shows the plan first, and nothing in the documents folder moves until *Apply*. Planning copies the mod into the Library, which the window now says; the loose files in `override` are adopted under a name you type. The adopted mod then shows in the Library as active, and its backup in *Changes*.
- The window's Mods tab has a *Load order* (P2.5-05): the active mods, lowest priority first, with *Up* and *Down*, and each file more than one of them ships with whose copy the game gets. Moving a mod shows the new winners and the plan at once; nothing changes until *Apply*, which is backed up and journaled like any change, and *Back to the saved order* drops the edit. An order that changes no file says so and has nothing to apply.
- The window has a *Fixes* tab (P2.5-06), as `fixes apply`, `fixes remove`, `fixes status`, `fixes rollback` and `fixes recover`: *Apply* and *Remove* for the 4 GB patch, *Install from a release* (a DXVK `.tar.gz`, `.zip` or `d3d9.dll` you downloaded) and *Remove* for DXVK, each showing its plan first and changing nothing until *Apply*. Each fix DAORework applied is shown as in effect, or as undone outside DAORework, which is what Steam's *Verify integrity* or a game update does, with the files it changed. Its backups are listed, most recent first, each with *Roll back to before this*, asked once more before anything is put back; a fix change that did not finish offers *Finish it* or *Roll it back*.
- A first-run flow (P2.5-07): the first profile you create is diagnosed at once, and every diagnosis ends in *Next steps* on the Profile tab: the 4 GB patch when it is off (`DAO_LAA_DISABLED`), DXVK when it is not installed, and adopting the mods you installed by hand when there are any. Each button switches to the tab its plan or list is on and opens it; nothing changes until you apply it there.
- Programs in mods are never installed ([ADR-0018](docs/adr/0018-mod-safety.md), P2.5-12): a file Windows runs or loads (`.exe`, `.dll`, `.bat`, `.ps1`, `.js`, `.msi` and the like) is left out of every mod change, and the plan names it and says why; a bundled DXVK `d3d9.dll` points to `fixes apply dxvk`. `mods import` and `mods library` name a mod's program files, and the adoption scan says adopting leaves them where they are. A program a previous version placed is removed by the next change. Managed fixes are unaffected. A program renamed to look like data (a file that starts with a Windows executable header) is caught too: each file's kind is recorded at import.
- `mods adopt --dry-run [--files]` (P2.5-02, [ADR-0015](docs/adr/0015-adopting-hand-installed-mods.md)) lists the mods installed by hand that DAORework could take over: each registered add-in with its folder in the documents folder (`addin:<uid>`), each folder in `override` (`override:<folder>`), and the loose files in `override` together (`override:(loose)`), with its size and its catalog entry when one matches. It also says what cannot be adopted and why: official DLC (never), an add-in whose folder is not in the documents folder, a folder in `AddIns` the game does not load. A candidate that is a mod already in the library (same files, same SHA-256, where DAUpdater.exe or the mod's own layout puts them) says so, since adopting it imports nothing new; a near match says how many files differ. A mod in a folder Vortex deploys into is flagged, since Vortex may undo a move. The window shows the same list under *Installed by hand* on the Mods tab.
- `mods adopt <id>... [--name <name>] [--files] [--dry-run] [--yes]` (P2.5-03, ADR-0015) takes those mods over without reinstalling them: it shows the plan, asks, backs up and applies, like `mods activate`. An add-in already where DAORework would put it is only recorded, and its `AddIns.xml` entry is left exactly as it is; an override folder or the loose files (named with `--name`) are moved into DAORework's own override folder, keeping their layout; when two adopted mods share a file name, the later one wins and the earlier copy is removed with a backup. A mod that is exactly one already in the library adopts as that mod; any other is imported into the library from its files first, recorded as adopted from its folder. Program files are left where they are. `mods rollback` undoes an adoption, moving every file back. The fault-injection suite kills `mods adopt` before every write in four adoptions (an add-in where it is, an override folder, the loose files, two folders sharing a file name) and recovers each kill both ways.
- Every release can be checked against how it was built ([ADR-0018](docs/adr/0018-mod-safety.md) §4, P2.5-12): the zip, `DAORework.exe` and `dao.exe` carry a GitHub build provenance attestation, which `gh attestation verify <file> --repo arastella625/DAORework` checks, alongside the `.sha256` as before. The release workflow can also code-sign the executables through Azure Artifact Signing once that is set up; this release is not signed, so Windows SmartScreen may warn on first run.
- The known-items catalog lists BioWare's official DLC (kind `Official`): Awakening and the ten DLC of the Ultimate Edition, by the 19 add-in UIDs in its `Settings\AddIns.xml`. Adopting hand-installed mods (P2.5-02, [ADR-0015](docs/adr/0015-adopting-hand-installed-mods.md)) uses it to leave the DLC alone. Diagnostics are unchanged: the DLC stays in `DAO_DLC_FOUND` and out of the known fixes and mods.

### Changed
- A Steam install is launched through Steam ([ADR-0022](docs/adr/0022-launching-steam-installs-through-steam.md)): *Launch game* and `launch` ask Steam to start Dragon Age: Origins (`steam://rungameid/47810`) instead of starting `daorigins.exe` themselves, so Steam starts it its own way, with the overlay and playtime. Steam opens first if it is closed, and runs what its Play button runs, so the profile's launch target does not apply to a Steam install. Launch arguments are passed through Steam, which asks to confirm them. GOG, EA App and hand-placed installs start the executable as before.
- The 4 GB patch is no longer applied to Steam's protected executable ([ADR-0023](docs/adr/0023-steam-protected-executable.md)). Steam's `daorigins.exe` carries Steam's copy protection, and Steam stops a changed copy with "Application load error 3:0000065432", which the owner's real Steam run hit. DAORework recognises the protection (detection only; it never removes it), refuses the patch there (`DAO_FIX_STEAM_PROTECTED`), stops suggesting it, and says so on the Diagnostics tab (`DAO_STEAM_EXE_PROTECTED`). A Steam copy that already has the patch gets a warning with how to undo it (`DAO_STEAM_EXE_PATCHED`). DXVK stays available. Copies without the protection, such as GOG and EA App, are patched as before.
- DAORework's license is now the PolyForm Noncommercial License 1.0.0 instead of MIT ([ADR-0020](docs/adr/0020-license-noncommercial.md)): it stays free, and anyone may use, change and share it or build on it for any noncommercial purpose, but nobody may sell it. Every earlier version was only ever published in the private repository.
- A library mod's `mod.json` is schema 3 ([ADR-0018](docs/adr/0018-mod-safety.md)): each file is recorded as data or a program, and the mod carries its antivirus verdict (*not scanned* until the scan lands). Entries written earlier are classified once from their files the next time the library is read; nothing needs importing again.
- Mod changes can move a file inside the documents folder, which adopting hand-installed mods will use ([ADR-0015](docs/adr/0015-adopting-hand-installed-mods.md)): the move is a rename, its backup records the move instead of a copy, and a rollback moves the file back (or copies it from the library by its hash if it is gone), never over a different file. Backups and the journal of a change in progress are schema 2; those written by 0.2.0 still read, and ones from a newer DAORework are refused rather than misread. Nothing plans a move yet.
- A library mod's `mod.json` is schema 2: it records the mod's `origin`, a download or (once adoption lands, [ADR-0015](docs/adr/0015-adopting-hand-installed-mods.md)) a mod adopted from the documents folder with the path it came from. Entries written by 0.2.0 are read as downloads; nothing needs importing again. A `mod.json` from a newer DAORework is refused rather than replaced.
- The app has its own look (P2.5-10, [ADR-0016](docs/adr/0016-gui-themes.md)): it opens in the dark *Witch of the Wilds* theme, near-black violet and plum with a violet accent, instead of following the system's light or dark mode. Every control takes the theme's colors, and a glow marks the button under the pointer or with keyboard focus. Three more themes are built in, *Korcari* (no glow), *The Fade* and *Blood and Shadow*; choosing one comes with the Settings page. Every theme passes WCAG AA contrast, which the App tests check. Buttons have an outline, and the selected tab is underlined with the theme's gradient. The shared look the pages are moving onto is in place: Cinzel for titles (SIL Open Font License 1.1, its license in the release zip), framed cards with corner filigree, a rune under page titles, severity rows with an icon and a word, callouts, confirm-dialog panels and a faint smoke and grain behind the page, all drawn for DAORework. Every page now uses it: the feather in the header, a titled page with its rune, framed cards with the facts in columns, Diagnostics rows with an icon, the severity's word and a colored stripe, and status lines in witch-green or the danger red instead of the old fixed green and red. The chosen theme is kept in `preferences.json` in the app-data folder and applied when the app starts; a missing, unreadable or unknown choice falls back to *Witch of the Wilds*, with a warning in the log (`DAO_PREFERENCES_UNREADABLE`). A new Settings page shows the four themes as cards, each with its colors; picking one changes the app at once and saves it.

## [0.2.0] - 2026-10-06

Phase 2 (mod manager), the first release that writes to your folders: a mod library, activating and deactivating mods with a plan, a backup and rollback, and the 4 GB patch and DXVK as managed fixes. Every change survives the process being killed at any write (the exit gate, ADR-0014). Verified on a real Steam install; GOG and EA App installs still need a real run ([#5](https://github.com/arastella625/DAORework/issues/5)).

### Added
- The known-items catalog (P1-07, ADR-0009 tier 1, [ADR-0011](docs/adr/0011-known-items-catalog.md)): `catalog/known-items.json` lists community fixes and mods with a source link, a license and fingerprints, and every diagnostic run now reports which of them are installed (`DAO_KNOWN_ITEMS_FOUND`). DXVK is recognized by the version string inside its `d3d9.dll` and reported with that version; a 64-bit DLL the 32-bit game cannot load is flagged (`DAO_KNOWN_ITEM_WRONG_ARCHITECTURE`); a missing DXVK is suggested with a link (`DAO_KNOWN_ITEM_SUGGESTED`); a `d3d9.dll` from something else is reported as unrecognized rather than as DXVK. Qwinn's Ultimate DAO Fixpack and Extra Dog Slot are recognized by the add-in UIDs in their `.dazip` manifests. The 4 GB patch is listed when the flag is set. Known-incompatible combinations are reported once both sides are in the catalog. All report-only.
- A mod library (P2-07, [ADR-0012](docs/adr/0012-mod-storage-model.md)): `mods import <path>` adds a `.dazip`, a `.zip` (a Nexus download with a `.dazip` inside works too) or an extracted mod folder to `%LOCALAPPDATA%\DAORework\library`, and `mods library` lists what is there. An add-in is named from its `Manifest.xml`; an override download from its file name without the Nexus suffix. Importing installs nothing and never touches the game or documents folders; an archive with a path that would leave the library is refused, and a `.7z` or `.rar` has to be extracted first. The same download imported twice is recognized.
- Mod activation (P2-06, [ADR-0012](docs/adr/0012-mod-storage-model.md)): `mods activate <id>...`, `mods deactivate <id>...`, `mods status`, `mods rollback [--backup <id>]` and `mods recover --finish|--rollback`, each on a profile's documents folder (`-p`, default `Default`). Every change shows its plan first (`--dry-run` stops there, `--files` lists each file) and asks before applying; `--yes` applies without asking, and a script that did not pass it is refused. Add-in files go to `AddIns\<uid>\` with their entry added to `Settings\AddIns.xml`; override files go to DAORework's own `packages\core\override\DAORework\<id>\`. A file DAORework did not put there is never overwritten (the plan is blocked), deactivating removes only what DAORework installed and its `AddIns.xml` entries, and `mods rollback` puts back the folder as it was before the last change from that change's backup. `AddIns.xml` keeps its byte order mark, declaration and line endings, so activating and deactivating leaves it byte-for-byte as it was.
- The 4 GB patch as a managed fix (P2-08, [ADR-0013](docs/adr/0013-managed-fixes-in-the-install-folder.md)): `fixes apply laa` sets the large-address-aware flag in `bin_ship\daorigins.exe`, the change the community 4GB Patch makes, through the same plan, confirmation, backup and journal as a mod change. Only the flag and the header checksum change; the unpatched exe is kept in the library, and `fixes remove laa` or `fixes rollback` puts it back byte for byte. `fixes status` shows what is applied and says when Steam's *Verify integrity* has put the original back. A game that is running, or an install DAORework cannot write to without administrator rights, blocks the plan; DAORework never asks for elevation. The `DAO_LAA_DISABLED` diagnostic now names the command. Both executables declare `asInvoker` in their manifest.
- DXVK as a managed fix (P2-08, [ADR-0013](docs/adr/0013-managed-fixes-in-the-install-folder.md)): `fixes apply dxvk <release>` takes the `x32\d3d9.dll` from a DXVK release you downloaded (the `.tar.gz` as GitHub publishes it, a `.zip`, an extracted folder, or the DLL itself), checks it against the known-items catalog's DXVK fingerprint and that it is the 32-bit build, keeps it in the library, and places it in `bin_ship` with a backup. A `d3d9.dll` already there is replaced only when it is DXVK too, and one placed by hand is kept so `fixes remove dxvk` puts it back; ReShade or any other wrapper blocks the plan. Nothing is downloaded by DAORework.
- The Phase 2 exit gate ([ADR-0014](docs/adr/0014-fault-injection-exit-gate.md)): a test suite kills the real CLI before every one of its file-system writes while it activates, deactivates and switches mods, applies and removes the 4 GB patch and applies, upgrades and removes DXVK, then recovers each kill both ways and checks the folders end exactly as before or exactly as after. It found the two fixes below.
- `scripts/catalog-fingerprint.ps1` prints the add-in UIDs and file lists a new catalog entry needs from a mod's download, without installing it.

### Removed
- The dev container (`.devcontainer/`). Development happens on Windows with the SDK from `global.json` and PowerShell 7, where the verify script can reach the game install.

### Fixed
- `mods rollback` and `fixes rollback` now undo the last change that actually happened. Each deployment record names the backup taken for the change that produced it. Before, a change killed after its backup but before its journal left a backup that rollback took for the newest change, so it did nothing. A rollback back at the very first change now says there is nothing more to undo.
- The 4 GB patch's write check no longer creates a file in `bin_ship`; it opens a file already there for writing and closes it. A check cut short could leave a `.daorework-write-check` file in the game folder.

## [0.1.0] - 2026-09-29

The first build to download and run: `DAORework.exe` (the window) and `dao.exe` (the CLI) for Windows, self-contained, so no .NET install is needed. Phase 1 (companion v1) continues with the known-items catalog (P1-07) and the Steam, GOG and EA App test matrix.

### Added
- `DAORework.App`, the desktop window on Avalonia (P1-00, ADR-0010): a profile selector with a *Create* box, a **Profile** page with Browse buttons for the install folder, game and launcher executables and documents folder plus the launch-target choice, a **Diagnostics** page that runs the rules and lists the issues, a **Mods** page that inspects the override and AddIns folders and writes the inventory, and a **Launch game** button. Every action goes through the same use cases as the CLI; reports land in the same app-data folders. Run it with `dotnet run --project src/DAORework.App`.
- `DAORework.App.Tests` renders every page on Avalonia's headless platform and saves the screenshots CI uploads.
- Real install detection (P1-01): the Steam copy on any library drive (through `libraryfolders.vdf` and the app manifest), the GOG copy through GOG Galaxy's registry keys, and the copy the EA App, Origin or the retail installer registered under `BioWare\Dragon Age`; the usual Program Files folders remain the fallback. `detect --path <folder>` checks a folder of your choosing. The Profile page gains a *Detected installs* section with a *Use* button per install.
- Documents folder detection (P1-02): the Documents folder Windows reports, the classic `%UserProfile%\Documents`, and `%OneDrive%\Documents` are all checked for a `BioWare\Dragon Age` folder. A new profile uses the one that exists. `detect` lists them, the Profile page's detected section offers them with *Use*, and two new diagnostics warn when the configured folder is empty while another has the saves (`DAO_DOCUMENTS_DIRECTORY_ELSEWHERE`) and when the folder in use is synced by OneDrive (`DAO_DOCUMENTS_ONEDRIVE_REDIRECTED`).
- The full diagnostic rule set (P1-03), all report-only: whether `daorigins.exe` is large-address-aware (the 4 GB flag, read from the PE header; `DAO_LAA_*`), the DirectX 9 June 2010 and Visual C++ 2005 runtimes (`DAO_PREREQ_*`), the game's `DragonAge.ini` with its resolution sanity-checked (`DAO_CONFIG_*`), save-folder health with empty save files and very large save counts flagged (`DAO_SAVES_*`), and the DLC and add-ins registered in `AddIns.xml` by title (`DAO_DLC_*`). None of them blocks a launch.
- Support bundle export (P1-04): `support-bundle [profile]` and an *Export support bundle* button on the Diagnostics page write one zip to the reports folder with the profile, a fresh diagnostic run, the mod inventory and the last week's logs (newest five, 1 MB each). The folder after `Users\` or `home/` and the account name are replaced with `<user>` in every entry.
- Save-game backups (P1-05): `saves backup [profile] [--keep N]`, `saves list [profile]` and a *Saves* tab copy every file under the documents folder's `Characters` into a zip in `%LOCALAPPDATA%\DAORework\save-backups\{profile}`, with a manifest. The saves folder is only ever read. After each successful backup only the newest N (default 10) are kept; retention deletes nothing outside DAORework's own backup folder.
- Release packaging (P1-06): a GitHub Actions workflow builds the Windows zip on every pull request that touches the apps (attached to the run for testing) and publishes it as a GitHub Release when a `v*` tag is pushed. The zip carries `THIRD-PARTY-LICENSES.md`, generated from the packages actually shipped, and the .NET runtime notices.

### Changed
- CLI output that is redirected (scripts, CI) is no longer wrapped at 120 columns, so long file paths stay on one line and can be read back (found by the owner's verify script, P1-04).

## [0.0.1] - 2026-09-29

The end of Phase 0 of the [roadmap](docs/ROADMAP.md). This tag marks the hardened foundation;
there are no published binaries yet (the first build ships with 0.1.0, task P1-06).

Phase 0 rebuilt the starter on the architecture in [docs/SDD.md](docs/SDD.md). The
CLI does what it did before, with the fixes listed under *Fixed*.

### Added
- Software Design Document, engineering standards, phase-gated roadmap, current-state audit and ADRs 0001–0010 (P0-01).
- `DiagnosticCodes`: one catalog of stable `DAO_*` codes (P0-02).
- Quality gates: .NET 10, warnings as errors, analyzers and StyleCop, central package management (P0-03); a CI workflow with format check, build, tests, an 80% coverage floor on Core and Application, and a 300-line file-size gate, plus PR and issue templates (P0-04).
- Five test projects, including architecture tests that enforce the dependency rules and forbid direct I/O outside Infrastructure (P0-05).
- `GamePaths`, `ByteSize`, `ProfileName` value objects, `Result<T>`/`Error`, and one `JsonDefaults` for every JSON document (P0-06).
- Ports for the machine: `IFileSystem`, `TimeProvider`, `IProcessLauncher`, `IFileHasher`, `IKnownFolders` (P0-07).
- `profiles` / `profile list` command (P0-12).
- Exit codes: `0` success, `1` expected failure, `2` invalid usage, `70` unexpected error (P0-12).
- `schemaVersion` on every persisted document, with a v0 → v1 migrator for profiles saved by earlier builds (P0-13).
- MIT license, `THIRD-PARTY-NOTICES.md`, and the third-party mods and tools policy (ADR-0008, ADR-0009).
- `scripts/verify-real-install.ps1`: the owner's check against a real install, run before every code PR.
- A dev container matching CI (the SDK from `global.json`, PowerShell 7) and Dependabot for NuGet and GitHub Actions (P0-15).

### Changed
- The CLI runs on Spectre.Console.Cli: one command class per verb, renderers, `--help` on every command; the old `help` verb is gone (P0-12).
- Diagnostics are one `RunDiagnostics` use case over one `IDiagnosticRule` per check (P0-08); mod inspection and inventory are use cases (P0-09); launching is the `LaunchGame` use case with runtimes chosen by keyed DI (P0-10); profile creation and editing are use cases, and each layer registers its own services through `DaoReworkOptions` (P0-11).
- Domain models are immutable records with read-only collections (P0-07).
- Report file names carry milliseconds and a random suffix, for example `dao-runtime-report-20260929-171818-569-33f5.json` (P0-13).
- Serilog console output is limited to warnings; the daily log file keeps everything (P0-12).

### Fixed
- The one test in the starter had been failing since a code rename (P0-02).
- Launch arguments containing spaces were split in two; they now go through `ArgumentList` (P0-07).
- Mod folder read errors are reported per file instead of being swallowed (P0-09).
- `launch` no longer saves the profile as a side effect (P0-10).
- Profile names are validated up front and stored verbatim, so a name no longer changes between save and list (P0-06); legacy profiles with a sanitized name are migrated to the file name (P0-13).
- Two reports written in the same second no longer overwrite each other (P0-13).
- A failed save no longer leaves an empty profile file behind; writes are atomic (P0-13).
- Unexpected errors no longer exit with code 0 (P0-12).
- Report JSON uses one consistent camelCase naming (P0-06).
- The README tree and command list are correct again (P0-14).
